# OCR shortlist: formal verification and Lean→Rust feasibility

**Research note — 2026-11-05**
**Sequence:** quality comparison first (#22/#25), then proof and Lean→Rust feasibility. This note follows that order. It does not select the production model or claim that local quality is already comparable end to end.

## 1. Quality checkpoint: what is and is not comparable

The current evidence is in [the local GPU comparison](local-gpu-ocr-evaluation.md) and the public-source comparison in [issue #22](https://github.com/guility/eOCR/issues/22). The diagnostic local shortlist spans PaddleOCR-VL-1.6, MinerU2.5-Pro-2605, WeVisDoc-4B, LightOnOCR-3-4B, OvisOCR3, dots.mocr, MonkeyOCRv2-B-Parsing, MiniCPM-OCR-1.0, GLM-OCR and Xiaomi-OCR-0. TeleOCR remains unscored because its supported parser path and source licensing are unresolved.

Some evidence overlaps, but it does not establish product-level equivalence:

- On the same six synthetic page images, candidate-native calls gave body CER of 0.0010 for MinerU2.5-Pro-2605, 0.0030 for WeVisDoc-4B and 0.0189 for LightOnOCR-3-4B. Each emitted the authored formula string on 6/6 pages. They used different task prompts, model APIs and output schemas.
- On one lightly audited English page, those three had 7, 39 and 34 character edits over 3,090 reference characters, while separate OvisOCR3 Markdown and PaddleOCR-VL OCR-task calls had 5 and 0 edits. These are single calls through candidate-native paths, not evidence of broad relative quality.
- On the checked Chinese page, several systems reproduce the annotated title and abstract exactly. The transcript covers only those sections, not the full page.
- PaddleOCR-VL-1.6 is the only candidate in this cohort exercised through a supported full PDF parsing pipeline. The other local calls generally consumed rendered page images, and no candidate produced a DOCX in these runs.
- Seed geometry results overlap on coarse table/image localization, but text-region granularity, formula classes and reading-order coverage are not consistent enough for a cross-candidate structural score.

The published benchmark figures are protocol-specific; different benchmarks, candidate subsets and author-run settings cannot be combined into the single weighted score proposed in #17. The defensible conclusion is **overlapping signals on narrow text and coarse-layout slices, with no product-quality winner yet**. #25 closed as completion of the diagnostic comparison/shortlist, not product acceptance; #17 and model/backend selection #14 remain open.

## 2. Accepted proof boundary

Issue #15 records the current requirement:

- The verified path includes preprocessing, orchestration, tensor transformations and ownership, model/backend operations, all invoked GPU kernels, and postprocessing to structured OCR output.
- CUDA compiler/toolchain, driver/runtime and physical GPU are an explicit trusted computing base (TCB). Theorems are relative to a pinned execution model and do not claim to verify the TCB itself.
- For a fixed inference graph and permitted shape range, the target claims are exact operation/copy/launch counts, peak live-buffer bounds, tight time/memory bounds in an explicit cost model, and justified absence of unnecessary work. Global optimality requires a defined allowed implementation family and objective; equivalence alone cannot prove minimality.
- Lean may prove that the structural validator correctly checks a PDF/DOCX result against an annotation: element presence/count, reading order and relative geometry within tolerance. It cannot establish that the annotation is true or that the OCR transcription is correct.

Finite resource bounds also need finite input limits. Pin maximum page raster dimensions/tiles, batch/concurrency, prompt and generated-token caps, model configuration, and streaming policy. Otherwise a fixed peak-memory maximum is undefined for arbitrary PDF sizes. Any token cap must be reported with its truncation and quality effects.

## 4. What Lean, GPU-kernel tools and Lean→Rust can support today

### Lean→Rust

Lean documents C and LLVM compiler backends, not an official CUDA backend. A theorem about a Lean definition does not prove generated Rust computes that definition. Lungo is a real Lean→Rust path and useful template experiment, but its own trust documentation says its backend is not proved and uses differential tests against Lean's native backend. Peregrine's backend matrix marks its Rust backend and printer unverified. Neither route produces a verified CUDA inference runtime. ([Lean compilation reference](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/), [Lungo trust boundary](https://machinefabric.com/lungo/docs/explanation/trust-and-verification), [Peregrine backend matrix](https://github.com/peregrine-project/peregrine-tool/blob/master/doc/backends.md))

The practical route is an eOCR-specific typed inference IR with explicit shapes, dtypes, buffers, copies, allocations, launches and synchronization; Lean specifications and cost semantics over that IR; then a restricted Rust host and kernel-source backend. Generated artifacts need proved refinement or translation validation against Lean semantics. External framework calls are opaque assumptions and cannot satisfy the whole-runtime claim. Lungo can help bootstrap Rust generation/template work, but generated code is not proof evidence.

### GPU kernels

- **LARK** is the closest surveyed Lean-based per-kernel equivalence approach. It proves kernel behavior against a Torch specification in a formal machine model. It is not a drop-in for our measured BF16 path: arithmetic is idealized as exact, allocation bounds are not modeled because memory is unbounded, floating-point behavior is tested rather than proved, and the operation set refuses BF16, 8-bit types, TMA, WGMMA, atomics and more. Extending the semantics/proofs or changing precision would be research; changing precision also requires re-evaluating OCR quality and resource use. It does not prove tight physical latency, global minimality or the framework/compiler chain. ([paper and assumptions](https://arxiv.org/html/2611.02028v1))
- **Lean Kernel Verify (LKV)** uses Lean to check selected Blackwell TLX/Triton and CuTe kernels for concrete cases: bounds, writes, hangs and selected barrier/TMEM conditions. Its stated limits exclude numerical correctness, performance, general all-shape guarantees, CUDA C++ and general race/deadlock freedom. It can add safety checks for kernels expressed in its supported DSLs, but not full model equivalence or resource/optimality claims. ([LKV scope and limits](https://github.com/facebookresearch/lean_kernel_verify))

The local OCR runs use vLLM, SGLang, Transformers and Paddle runtimes. Public model pages document invocation, not the exhaustive kernels selected for each dtype, image shape, token length, batch/concurrency state and GPU. The exact kernel set, fallbacks and allocations require a frozen runtime trace plus source/binary inventory. A kernel that cannot be covered must be verified or replaced to satisfy #15; it cannot be an undocumented exception.

CUDA produces versioned device artifacts: source may become PTX and then an SM-specific cubin; PTX may instead be JIT-compiled by the installed driver. The agreed TCB trusts those tools/hardware but still requires pinning the artifact and configuration. Reject unvalidated fallbacks/JIT paths or validate them as separate configurations. ([CUDA platform/toolchain model](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/01-introduction/cuda-platform.html))

### Tight bounds and “no unnecessary work”

For a fixed graph and explicit shape/token range, Lean can reason about exact operation/copy/allocation/live-buffer/launch counts and symbolic resource bounds. A separate refinement must connect these to emitted Rust, kernel IR, binaries and actual runtime calls. Current LARK/LKV work does not supply that full chain.

“Unnecessary” needs definition. We can prove that a named implementation has no dead graph nodes, duplicate transforms, redundant copies or avoidable buffer materializations relative to specified rewrites and a cost objective. A lower bound or claim that no faster/smaller equivalent implementation exists requires a defined implementation family and a proved lower bound. GPU wall-clock time additionally depends on launch overhead, bandwidth, occupancy, scheduling, clocks/thermal behavior and contention; abstract op counts do not imply physical latency. Peak VRAM can be bounded more directly once allocation/liveness and concurrency assumptions are fixed, then tied to a specific runtime/kernel configuration.

## 5. Recommendation and next gate

1. **Do not select PaddleOCR solely because its full PDF path was easiest to exercise.** The quality comparison has no winner; Paddle's Russian and structural results matter.
2. **Carry a representative proof-feasibility set, not a production model decision:** PaddleOCR-VL-1.6 as the full PDF/layout trace baseline; MinerU2.5-Pro-2605 as the Qwen2-VL/two-stage path; LightOnOCR-3-4B as coordinate-bearing Qwen3.5, with OvisOCR3 as its smaller same-family alternative; and dots.mocr as a conditional custom structured-output path. Keep MonkeyOCRv2 eligible once supported GPU inference is reproducible. WeVisDoc, GLM-OCR, Xiaomi-OCR-0 and MiniCPM-OCR remain in quality comparison, but current product-contract/inference evidence does not justify separate first proof prototypes.
3. **Do not begin full proofs yet.** Next evidence: representative frozen corpus and weighted-score protocol (#17/#25), selection of one exact model/runtime/backend/configuration (#14), and exhaustive GPU trace of that route. No surveyed OCR framework is proof-ready for the accepted whole-runtime boundary.
4. **After the quality gate, prototype in thin vertical slices:** one pinned model and inference shape with its full kernel inventory; then input contracts, preprocessing, kernel semantics/refinement, postprocessing and cost traces; finally PDF/DOCX structure and validator claims. This first slice is a feasibility experiment, not evidence that the product passes its quality score.
