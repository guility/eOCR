# OCR shortlist: formal-proof and Lean→Rust feasibility

**Research snapshot:** 2026-11-04  
**Scope:** static audit of public local inference paths for the quality shortlist in [issue #22](https://github.com/guility/eOCR/blob/research/frontier-gpu-ocr/docs/research/frontier-gpu-ocr.md), in response to [issue #24](https://github.com/guility/eOCR/issues/24). No models, GPU kernels, benchmarks, tracing, or proofs were run.

## Finding

No candidate is proof-ready as a complete inference runtime. Every path reaches GPU execution through a framework/runtime plus libraries and shape-dependent kernels; public model and pipeline code does not enumerate the kernels selected for every input, dtype, batching, device, and runtime setting. Under the accepted [issue #15 proof boundary](https://github.com/guility/eOCR/issues/15#issuecomment-6625457878), all active kernels must be proved against the chosen execution model or replaced, while CUDA compiler/driver/runtime and the physical GPU remain explicit trusted components. A source-only review cannot establish runtime-exhaustive kernel coverage.

For **proof feasibility only**, Xiaomi-OCR-0 and GLM-OCR are the most legible model-only paths in this static review; PaddleOCR-VL-1.6 is the integration/trace anchor because it is already selected and its VLM request was smoke-verified in #19. This is not a model or proof-prototype selection. A prototype should be chosen only after the quality shortlist has been checked locally and the candidate runtime's kernels have been traced. Xiaomi has a documented native Transformers path based on a published Qwen3.5 architecture; GLM has owner-documented Transformers and local vLLM/SGLang paths plus upstream vLLM model support. Their model-path source boundary is comparatively legible, but PyTorch/vLLM kernels are not proved. Paddle has the clearest pinned vLLM model revision/runtime in this project, but its document pipeline adds a separate PP-DocLayoutV3 stack. MiniCPM adds a selectable FlashAttention backend and optional DSpark draft model; Ovis explicitly selects a Triton GDN prefill backend; TeleOCR and Youtu add project-specific vLLM plugins. These are additional proof surfaces, not measured differences in OCR quality or speed.

### Kernel classes and opaque library boundary

Across the standard VLMs, **inferred** kernel classes include image patch embedding/projection, dense or quantized GEMM, attention, normalization/activation/position operations, and token sampling. A DETR/Paddle layout stage adds image feature extraction, transformer blocks, box/class heads, resize/crop and suppression operations. This is an architecture-derived checklist, not a measured runtime inventory. The owner sources explicitly name FlashAttention for MiniCPM and Youtu, Triton GDN prefill for Ovis, and PyTorch/xFormers dependencies plus a project vLLM plugin for TeleOCR. They do not establish whether a particular call uses cuBLAS, cuDNN, CUTLASS, FlashInfer, a Triton specialization, or a fallback kernel. Those providers, dispatch decisions, generated kernels and their artifacts remain opaque until traced for each frozen shape/dtype/configuration.

## What the available proof tools cover

- [LARK](https://arxiv.org/abs/2611.02028) is a proof approach for individual CUDA/PTX/HIP kernels against a formalized reference, with modeled safety and termination properties. Its published limitations include exact rather than hardware floating-point arithmetic, unbounded modeled memory, unsupported operator refusal, and missing support for several modern GPU features/dtypes. It is not a complete OCR-runtime checker and does not prove performance-optimality.
- [Lean Kernel Verify (LKV)](https://github.com/facebookresearch/lean_kernel_verify) checks selected Blackwell TLX/Triton and CuTe DSL cases for safety properties such as bounds and selected synchronization protocols. The project states that it does not prove numerical correctness or performance, and its case verdicts are shape/configuration specific. A candidate's use of Triton does not imply that its kernels match LKV's supported inputs.
- [Lean's documented compiler and FFI](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Foreign-Function-Interface/) provide C/LLVM/native compilation and C ABI interop, not a proved Rust/CUDA target. [Lungo](https://github.com/machinefabric/lungo-rs) can emit Rust through Lean compiler IR, but its own trust/verification documentation says differential checks are not a proof of the Rust backend. [Peregrine](https://github.com/peregrine-project/peregrine-tool/blob/master/doc/backends.md) marks its Rust backend unverified. Neither closes Lean→Rust→CUDA refinement.

Thus the difference between candidates is primarily **how many code/runtime surfaces must be frozen and audited**, not whether any vendor currently supplies the requested proof. A Lean graph/shape/cost model can cover each candidate in principle; obtaining a theorem about the deployed executable requires refinement/translation validation through generated host code, every selected GPU kernel and its final target artifact. It also requires an explicit family of allowed implementations before “no unnecessary operations” or lower-bound optimality is meaningful.

## Next evidence before choosing a proof prototype

First evaluate the quality shortlist locally using the agreed corpus and metrics; this note does not select a model or combine public scores. Once that produces viable candidates, freeze a single-image, one-dtype, greedy-decoding model-only path for one or two of them, pin model/framework revisions, image-size/token bounds and GPU target, and capture actual kernel/library names and fallback decisions for each supported shape. Then estimate whether each kernel can be expressed in LARK's supported subset, whether selected safety checks fit LKV, or whether a kernel must be replaced. Only then choose a proof prototype and write a small Lean operation/ownership/cost specification. Add PP-DocLayoutV3, PDF preparation, concurrency, dynamic shapes and DOCX assembly in later refinements. Runtime tracing and GPU measurement are required to claim the exhaustive inventory, real peak memory, or actual time; none is established by this note.
