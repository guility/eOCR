# PaddleOCR-VL-1.6 runtime and GPU-kernel source audit

**Research snapshot:** 2026-11-04. **Scope:** static source audit for issue [#24](https://github.com/guility/eOCR/issues/24); no inference, benchmark, or GPU tracing was run.

## Finding

The selected stack is a sensible OCR prototype, but the current PaddleOCR + vLLM composition is not presently evidence-ready for the agreed proof perimeter over the *whole* inference runtime. The VLM checkpoint and vLLM image are pinned, and vLLM has inspectable model code. However, the PaddleOCR/PaddleX client runtime and PP-DocLayoutV3 weights/configuration were not pinned by the smoke run; several kernel providers are compiled or dispatched below the Python model source; and the smoke exercised only the vLLM image endpoint, not PDF parsing, layout detection, cropping, or the client-to-server path. A complete kernel list, exact backend choices, and launch/allocation trace therefore remain unknown. [Issue #19 smoke record](https://github.com/guility/eOCR/issues/19#issuecomment-6620876329)

## Runtime path and dispatch

1. **PDF and page preparation.** Issue #19 rasterized a synthetic PDF page and posted that PNG to `/v1/chat/completions`; it did not call `PaddleOCRVL.predict(PDF)`. PDF parsing/rendering, digital-text/vector extraction, page partitioning, and eOCR's source-aware branch are therefore outside that measured path. [Smoke details](https://github.com/guility/eOCR/issues/19#issuecomment-6620876329)
2. **Layout frontend.** The candidate official config runs PP-DocLayoutV3 locally with PaddlePaddle, then provides layout regions to VLM recognition. PaddleX describes PP-DocLayoutV3 as DETR-based, with a PPHGNetV2-L backbone plus instance segmentation and reading-order prediction. That implies convolution/backbone, transformer/query-decoder, and mask/order-head operation families, but not an exact CUDA kernel list. PaddleOCR's layout API exposes `paddle_static`, `paddle_dynamic`, Transformers, and ONNX Runtime; the default local engine is documented as `paddle_static`. TensorRT acceleration and fp16/fp32 precision are configurable. The exact selected engine, precision, pre/postprocessing placement, and kernels are not in the smoke record. [PaddleX architecture docs](https://paddlepaddle.github.io/PaddleX/3.7/module_usage/tutorials/ocr_modules/layout_analysis.html), [PaddleOCR layout engine/config docs](https://github.com/PaddlePaddle/PaddleOCR/blob/dab3fe35379033fdcb2d0e9572fac0b36c9a9ebf/docs/version3.x/module_usage/layout_analysis.en.md)
3. **VLM image path.** The vLLM 0.32.0 source implements `PaddleOCRVLForConditionalGeneration` as a SigLIP vision transformer, a projector, and `Ernie4_5ForCausalLM`. The vision code constructs QKV and output projections, encoder attention, rotary position handling, layer norms, an MLP, and residuals. The language model adds transformer projections/MLPs, decoder attention, KV-cache access, logits, and token sampling. These establish operation *families*; they do not identify the concrete fused kernel or provider invoked for each operation. [Pinned model source](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/paddleocr_vl.py), [Ernie implementation](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/ernie45.py)
4. **Variable input shape.** The pinned image processor allows 112,896–1,003,520 pixels and 14×14 patches merged 2×2. This corresponds to 576–5,120 vision patches (144–1,280 merged image tokens) before batching, subject to processor/model overrides. vLLM's `smart_resize` also derives a patch-aligned size from model processor settings. Layout-region count, image aspect ratio, batch packing, prompt length, and generated token limit consequently change work and memory shapes. [Pinned processor/config files](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6/tree/c5630abae1d940eafe0697512a0325494b02ab42), [vLLM resize and processor logic](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/paddleocr_vl.py)
5. **Attention and precision choices.** vLLM resolves the vision attention backend through the active platform, head size, dtype, and optional multimodal override. The model source explicitly has branches for FlashAttention, Triton attention, and ROCm AITER; the shared multimodal attention implementation also contains other backend paths. For ordinary CUDA decoder attention, vLLM documents automatic backend selection by GPU architecture and compatible configuration (on Blackwell, priority begins FlashInfer, FlashAttention, Triton, then FlexAttention). Issue #19 did not pin `--attention-backend`, `--dtype`, KV-cache dtype, or multimodal encoder dtype. BF16 is declared in the checkpoint, but the exact loaded dtype and selected kernel versions must be taken from server startup/runtime diagnostics. [Vision backend dispatch](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/vision.py), [vLLM 0.32 attention selection](https://docs.vllm.ai/en/v0.32.0/design/attention_backends/)

## Kernel inventory versus proof coverage

| Source-visible family / provider boundary | Status from static source | LARK / LKV fit |
|---|---|---|
| Paddle layout: convolutional backbone, transformer/deformable or query attention, box/mask/order heads; possible norm/activation/resize/postprocess kernels | Architecture is documented, but Paddle/PaddleX dispatch, concrete Paddle GPU kernels, tensor layouts, dtypes, and host-vs-device postprocessing are not established for the deployed image. cuDNN/cuBLAS/TensorRT or framework custom kernels are provider candidates, not confirmed launches. | **Opaque until pinned and traced.** LARK could cover adapted kernels only where the operation table and semantics support them; LKV does not target generic Paddle CUDA kernels. |
| VLM dense projections, MLP/GELU, layer norm, RoPE, image patch/position transforms | Python module structure is visible. Actual fusion, allocator reuse, Triton/CUDA code selection, and library calls are not. | **Partial candidate.** LARK includes basic GEMM/linear, normalization, activation, RoPE, and some attention workloads, but requires its supported input language/operation subset and its stated assumptions. |
| VLM vision and decoder attention / KV cache | Backend selection is conditional; likely providers include FlashAttention, Triton, and FlashInfer, with possible CUDA/CUTLASS or generated kernels underneath. Exact provider/kernel, dtype specialization, tile/shape variant, graph-capture path, and KV layout need runtime evidence. | **Conditional/partial.** LKV can check supported Triton/TLX or CuTe DSL kernels for concrete case shapes, but not CUDA C++ or numeric correctness/performance. LARK can prove per-kernel equivalence only after translation/adaptation; it rejects bf16 and asynchronous TMA/WGMMA/mbarrier/atomics in the published operation tables. |
| Framework/runtime glue: allocation, H2D copy, stream/event synchronization, graph capture, server scheduler, optional TP collectives | Model source shows asynchronous host-to-device metadata transfer; issue #19 used tensor parallel size 1. Runtime allocators, launch sequence, memory lifetimes, stream behavior, and CUDA graph selection are unrecorded. NCCL communication is not exercised at TP=1. | **Unsupported as a whole-runtime claim.** Neither kernel tool alone proves host orchestration, framework code, dispatch, allocation bounds, or tight end-to-end costs. |

LARK proves selected per-kernel functional/memory equivalence, race freedom, modeled safety, and termination relative to its formal model; its paper states exact-arithmetic idealization and refuses operations including bf16, TMA, WGMMA, mbarrier, atomics, and other constructs. It does not provide tight physical latency/peak-memory bounds. LKV covers selected Blackwell Triton/TLX and CuTe DSL kernels with concrete case-shape checks for safety properties; it does not prove numerical correctness or performance, nor CUDA C++ kernels or every possible shape. [LARK limitations](https://arxiv.org/html/2611.02028v1#S6), [LKV scope and limits](https://github.com/facebookresearch/lean_kernel_verify)

**Recommendation:** retain this stack as a reference/prototype, but do not call it compatible with the full Lean proof perimeter yet. Under the agreed TCB (CUDA compiler/driver/runtime and physical GPU), Paddle/PyTorch/vLLM operator implementations and external GPU libraries are not automatically trusted; each must be proved/validated against the agreed model or replaced by controlled implementations. Current LARK/LKV could help classify and prove a restricted subset, but their current published scopes cannot discharge the whole runtime, all dtypes/shapes, or the requested end-to-end tight cost and no-unnecessary-work claims. [TCB decision](https://github.com/guility/eOCR/issues/15#issuecomment-6625457878), [repository Lean runtime assessment](lean-runtime-architecture.md)

## What remains unknowable without runtime instrumentation

Static source does not reveal which operators are fused, which shared libraries execute kernels, or all kernel names, launch dimensions, allocations, shapes, and dtypes after graph capture and batching. It also cannot establish the exact PP-DocLayoutV3 weight snapshot selected by `model_dir: null`, the actual Paddle/PaddleX client package versions, vLLM's resolved BF16/KV-cache configuration, backend fallbacks, or whether optional preprocessing is enabled in the deployed config. A complete inventory needs an instrumented `PaddleOCRVL.predict(PDF)` run on the pinned client and server images with the PP-DocLayoutV3 artifact pinned, varied page/region sizes, startup configuration captured, and CUDA API/kernel trace correlated to framework source and binaries. That next step is required before claiming runtime exhaustiveness; this note makes no such claim.
