# Lean proofs, runtime boundary, and CUDA compilation

**Research note — 2026-11-04**

**Post-quality follow-up:** candidate-specific formal-verification and Lean→Rust feasibility, based on the diagnostic OCR comparison in #25, is recorded in [ocr-proof-feasibility.md](ocr-proof-feasibility.md). Treat older model shortlist comments below as pre-quality source inventory, not model-selection guidance.

## Findings (documented facts)

- **Lean compilation choices.** Lake exposes `C` and `LLVM` as compiler backends. The Lean reference describes a module path that emits C and compiles it to native code; Lake also exposes LLVM bitcode artifacts, and the FAQ identifies LLVM as the default code-generation backend in its native-execution TCB discussion. These are Lean/native build backends, and the docs do not describe a CUDA or NVIDIA GPU backend. The last sentence is an inference from the documented backend choices and artifacts. ([Lake backend API](https://lean-lang.org/doc/api/Lake/Config/LeanConfig.html), [Lean compilation pipeline](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/), [Lake build artifacts](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/), [Lean FAQ](https://lean-lang.org/faq/))

- **Lean's proof/runtime boundary.** Lean's FAQ says that running verified Lean code as a native binary extends the trusted computing base to the Lean compiler, Lean runtime, code-generation backend, and all linked external code. The runtime supplies memory management/reference counting, representations and primitive operators, and task scheduling. Lean's compiler documentation also notes that `partial` functions are opaque to the kernel for reasoning and that `unsafe` functions bypass it. ([Lean FAQ](https://lean-lang.org/faq/), [Lean runtime](https://lean-lang.org/doc/reference/latest/Run-Time-Code/), [Lean compiler and kernel](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/))

- **FFI boundary.** `@[extern]` substitutes a foreign symbol for compiled Lean code; `@[export]` exposes Lean code through the C ABI. The ABI includes Lean-specific object representations and ownership/reference-counting rules; the `@&` borrowed marker changes runtime behavior but has no effect in Lean's type system. The reference calls the current FFI unstable. ([Lean FFI reference](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Foreign-Function-Interface/))

- **CUDA pipeline.** `nvcc` separates host and device code. Its device compiler emits PTX; `ptxas` turns PTX into a cubin for a physical SM architecture. A fatbin may carry multiple cubins and PTX targets. PTX can instead be JIT-compiled by the installed driver at runtime, so the exact device binary can depend on the deployed driver. ([NVIDIA NVCC workflow](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/nvcc.html), [CUDA platform, cubins and PTX JIT](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/01-introduction/cuda-platform.html))

- **Artifact inspection is not a correctness proof.** NVIDIA's `cuobjdump` can extract PTX and disassemble SASS from cubins, and report resource-use counts such as registers, stack, shared and local memory. Its documentation describes inspection and reporting, not semantic equivalence checking. ([CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/))

- **A Lean theorem is not automatically a cost theorem for the executable.** Lean explicitly notes that kernel-oriented recursive translations need not preserve the programmer's expected cost model (including laziness versus strictness); the compiler handles a different representation. ([Lean compilation pipeline](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/))

## Recommendation (architecture for eOCR)

Use Lean to define the OCR algorithm, typed inference IR, and end-to-end cost semantics, and to check proof certificates. A custom backend may be written against Lean's compiler IR, but the backend's output is not thereby verified. Generate a restricted Rust host path and GPU kernel IR from the same inference IR; make buffer ownership/lifetimes, tensor shapes, launches, synchronization, and every costed operation explicit. Keep the general Lean runtime out of the production inference hot path so its reference counting, allocator, and task scheduler do not become additional unverified runtime components. This is an architectural recommendation, not a capability provided by Lean out of the box.

For a whole-runtime guarantee, prove each relevant compiler/runtime refinement or translation-validate the exact artifacts and configuration being deployed. The chain must cover the Lean IR and proof checker, generation of Rust and kernel IR, Rust compilation/linking through host machine code, the Rust-to-CUDA-driver boundary, kernel compilation through PTX to final cubin/SASS, and all memory transfers/launches. NVIDIA documents `cuobjdump` inspection, not an equivalence checker, so SASS counts and disassembly alone do not close this gap. A verifier for exact host/GPU artifacts, or a proven compiler chain, is a prerequisite for the requested full proof claim. Pin and record the Lean version, custom backend/checker hashes, Rust toolchain, CUDA toolkit, target SM, driver, linked libraries, container image, and model/weight checksum. Ship target-specific cubin and reject driver JIT/fallback unless that path is also validated. The Lean FAQ's stated TCB and NVIDIA's separate PTX/SM/JIT stages motivate this boundary-by-boundary scope; the proposed checker/toolchain itself is future project work.

For **модель затрат**, first prove operation and memory bounds over explicit input/model shapes. Then connect those bounds to the specific device kernels and runtime path. `cuobjdump -res-usage` can provide useful static resource figures, but it does not by itself prove execution-time bounds. A hard latency guarantee additionally needs a justified cost model for the selected GPU, driver, memory behavior, scheduling, synchronization, and launch path; benchmark results alone are evidence for tested conditions, not a proof for all executions. ([Lean cost-model note](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/), [NVIDIA resource inspection](https://docs.nvidia.com/cuda/cuda-binary-utilities/), [NVIDIA PTX JIT behavior](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/01-introduction/cuda-platform.html))

Keep foreign/unsafe code narrow and give each boundary an explicit contract for value semantics, ownership/lifetimes, failure behavior, synchronization, and resource use. The kernel can establish guarantees relative to the contract and the stated model; it cannot establish that a human-authored reference annotation is true, or that an unvalidated compiler/runtime/kernel implementation satisfies the model. The annotation limit follows the repository's definition of **эталонная аннотация** in `GLOSSARY.md`; the implementation-boundary conclusion follows from Lean's documented TCB and FFI semantics. ([Lean FAQ](https://lean-lang.org/faq/), [Lean FFI reference](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Foreign-Function-Interface/))

## Current Lean-to-Rust code generation candidates (checked 2026-11-04)

The older interop note describes Lean's documented native C/LLVM paths. A third-party route has since been identified and should be considered separately from Lean's own compiler:

- **Lungo** builds Rust modules from Lean projects through Lean's compiler IR and a Rust port of the Lean runtime. Its published trust boundary includes the Lean toolchain, worker adapter, Bridge IR backends, Rust facade conversions, runtime primitives, and application host facilities. It validates input IR and differentially tests generated Rust against Lean's native backend, but its documentation explicitly says these checks are not a proof of the backend. This makes it useful for a Lean-to-Rust template experiment, but insufficient for the required production proof chain. ([Lungo README](https://github.com/machinefabric/lungo-rs), [architecture](https://machinefabric.com/lungo/docs/explanation/architecture), [trust and verification](https://machinefabric.com/lungo/docs/explanation/trust-and-verification))
- **Peregrine** has a Rocq-verified middle end, but its Rust backend is explicitly unverified. Its Lean frontend is partially verified and currently lacks Lean IO, Task, primitive arrays, and primitive floats. The documented pipeline does not compile GPU kernels. ([backend assurance matrix](https://github.com/peregrine-project/peregrine-tool/blob/master/doc/backends.md), [Lean frontend limitations](https://github.com/peregrine-project/peregrine-tool/blob/master/doc/frontends.md))

**Updated recommendation:** keep Lungo as a candidate for a disposable generator/template prototype only; do not use it as evidence that Rust output refines Lean proofs. No surveyed off-the-shelf path provides the requested end-to-end evidence for Lean-authored logic, Rust host code, GPU kernels, generated GPU code, tight resource bounds, and absence of unnecessary operations. The production design still needs explicit refinement proofs for the code-generation chain and a GPU execution/cost model. The user chose the CUDA compiler, driver/runtime, and physical GPU as an explicit TCB; see the [resolution of issue #15](https://github.com/guility/eOCR/issues/15#issuecomment-6625457878). This permits proofs relative to a pinned GPU execution model, but does not claim that the TCB itself is verified.

## Newer Lean-based GPU-kernel verification work (checked 2026-11-04)

Two recent projects narrow the research gap, but neither verifies the complete deployed OCR inference runtime or the requested optimality properties.

- **LARK** is a research framework that machine-checks per-kernel equivalence to a formalized Torch specification, race-freedom, absence of modeled faults, and termination for CUDA, PTX, and HIP kernels. Its source-to-Lean translation is deterministic and it exports a standalone Lean certificate. It is the closest surveyed design for proving individual kernels against a higher-level reference. Its guarantee is relative to a fixed Lean machine model and explicitly stated assumptions: operation semantics are measured against hardware; the Torch formalization is trusted and tested separately; the compiler/runtime that executes the kernel is not proved by the per-kernel theorem. Its arithmetic is idealized as exact (floating-point behavior is separately tested), modeled memories are unbounded (so actual allocation-bound safety is outside the theorem), unsupported operations are refused, and its documented operation table excludes features including TMA, WGMMA, mbarrier, atomics, bf16, and 8-bit types. The paper reports latency measurements, but no tight latency or peak-memory theorem and no proof of globally minimal operations/objects. Treat LARK as a proof architecture to investigate, not a turnkey eOCR runtime. ([paper](https://arxiv.org/abs/2611.02028), [full text: trust boundary and assumptions](https://arxiv.org/html/2611.02028v1), [limitations](https://arxiv.org/html/2611.02028v1#S6))
- **Lean Kernel Verify (LKV)** is a public Lean checker for selected Blackwell TLX/Triton and CuTe DSL kernels. It checks specific cases for address bounds/wraparound, output writes exactly once, selected barrier protocols, hangs, and some TMEM hazards. It operates on real compiler IR but only proves verdicts for the case-file shapes; its README says it does not check numerical correctness or performance, and does not check what lies below the compiler IR. Some phase-ledger soundness arguments are explicitly not proved, and general race/deadlock freedom is out of scope. It can supply useful kernel safety checks for supported cases, but not functional equivalence, tight costs, or whole-runtime assurance. ([project and limits](https://github.com/facebookresearch/lean_kernel_verify))

**Updated assessment:** these tools make a constrained, staged kernel assurance plan plausible: freeze every model/backend/kernel variant and shape; use per-kernel Lean equivalence proofs where the operation set is supported; reject or replace unmodeled kernels; and state cost theorems over an explicit operation/allocation trace. The agreed TCB narrows the required proof claim, but it does not make any selected OCR runtime verified. Proving a lower bound or absence of unnecessary operations requires a defined family of allowed implementations and a stated cost objective; equivalence alone cannot establish optimality. Tight abstract cost bounds also need a separate refinement connecting the source-level traces to compiled host/device artifacts. LARK and LKV do not close the Lean→Rust/CUDA code-generation chain or prove physical timing. The next source comparison of formal-verification and Lean→Rust feasibility across the quality shortlist is tracked in [issue #24](https://github.com/guility/eOCR/issues/24); exhaustive kernel inventory, runtime tracing, and latency/VRAM measurement come only after downselection.
