# Local PDF-route eligibility for the #26 comparison

**Checked 2026-11-05.** This memo answers whether existing OCR shortlist entries have an upstream local PDF-to-parser route, whether they need an added PDF render/page loop, and what the upstream code and weight licenses separately say. It does not establish eOCR PDF→DOCX quality or license advice. The requested [frontier shortlist note](https://github.com/guility/eOCR/blob/research/frontier-gpu-ocr/docs/research/frontier-gpu-ocr.md) was read from its committed branch because it is absent from this worktree; the local diagnostic is [here](local-gpu-ocr-evaluation.md). Issue #26 requires at least two eligible challengers to enter the representative corpus comparison, with the same source-aware extraction, DOCX builder, and rendering path.

## Eligibility result

**Strongest complete local challengers:** MiniCPM-OCR 1.0 and GLM-OCR have first-party local PDF parsing SDKs, along with declared permissive licenses for code and weights. MonkeyOCRv2-Parsing is another Apache-licensed first-party PDF parser with an official Russian MDPBench result, but its supported vLLM route previously failed in this project’s container with a UVA initialization error; treat it as a conditional runtime candidate. [MiniCPM SDK and license](https://github.com/OpenBMB/MiniCPM-OCR/blob/main/docs/minicpm_ocr_1dot0_en.md) · [GLM SDK and license](https://github.com/zai-org/GLM-OCR) · [MonkeyOCRv2 parser and license](https://github.com/Yuliang-Liu/MonkeyOCRv2) · [MDPBench results](https://huggingface.co/datasets/Delores-Lin/MDPBench) · [local runtime note](local-gpu-ocr-evaluation.md#deployment-failures-and-resources).

The “complete PDF route” below means upstream code accepts a PDF and performs parsing/inference to its own structured or Markdown result. It does **not** mean the model itself emits eOCR’s required DOCX, preserves PDF vectors, makes Word OMML equations, or detects/inserts signatures. All candidates still need the common downstream eOCR adapter and DOCX rendering required by #26. [Issue #26](https://github.com/guility/eOCR/issues/26) · [Paddle’s current PDF→DOCX diagnostic](local-gpu-ocr-evaluation.md#diagnostic-pdfdocx-slice-paddleocr-vl-16).

## Suggested #26 pilot set

Start with **PaddleOCR-VL-1.6, MiniCPM-OCR 1.0, and GLM-OCR**: all three have first-party full-PDF local parsing routes and declared permissive code/weight licenses, with separate structured output for the shared DOCX adapter. That gives two license-clear challengers immediately. Keep MonkeyOCRv2 as a high-priority reserve if the supported vLLM startup issue is resolved before the pilot. LightOnOCR-3 is another license-clear route with its own PDF/page wrapper, though the current local probe was page-image-only. These are eligibility recommendations, not quality selections; #26 still needs the representative corpus, common downstream DOCX path, Word rendering, and all #17 dimensions before any winner can be named. [Issue #26](https://github.com/guility/eOCR/issues/26) · [accepted #17 score protocol](https://github.com/guility/eOCR/issues/17).
