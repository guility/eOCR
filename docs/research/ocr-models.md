# Кандидаты full-cycle OCR-стека для eOCR

Контекст: [issue #2 — «Исследовать full-cycle OCR-модели и путь инференса»](https://github.com/guility/eOCR/issues/2).  
Дата исследования: 4 ноября 2026 года.  
Область v1: рукописный текст не распознаётся; подпись требуется обнаружить как отдельный визуальный объект и вставить в DOCX как raster image. Подпись не считается OCR-текстом.
Результат: shortlist для дальнейшей оценки; окончательная модель не выбрана.

## Краткий вывод

Для eOCR нужно оценивать не только распознающую модель, а фиксированный стек от чтения PDF до результирующего DOCX. Текущие кандидаты закрывают разные части задачи:

1. **MinerU 4.1** — наиболее полный готовый стек: native parsing цифрового текста, OCR сканов, VLM-путь для сложных страниц, структурированные данные и DOCX renderer. В light OCR stack сейчас указан PP-OCRv6 Small, который покрывает упрощённый и традиционный китайский, английский и латинские языки, но не русский; VLM-путь и текущая русская точность требуют отдельной проверки. Некоторые узлы явно исполняются на CPU, а выбор ONNX device допускает CPU fallback. У самого проекта есть дополнительные лицензионные условия поверх Apache 2.0. [MinerU tiers](https://opendatalab.github.io/MinerU/usage/tiers/), [model assets](https://opendatalab.github.io/MinerU/zh/next/model-assets/), [PP-OCRv6 language matrix](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.md), [license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)

2. **PaddleOCR-VL-1.6** — наиболее чёткое явное подтверждение русского языка среди рассмотренных VLM: в алгоритмической документации серии перечислены 109 языков, включая русский, но release notes VL-1.5 говорят о 111; полный перечень VL-1.6 требует подтверждения. Система состоит из PP-DocLayoutV3, 0.9B VLM и постобработки до Markdown/JSON. В языковом списке написано просто «Chinese»; отдельного подтверждения обеих разновидностей китайского для VL-1.6 не найдено. Серия поддерживает DOCX export, но документация не обещает точного сохранения исходной геометрии или редактируемых формул и графики. [PaddleOCR-VL-1.6 paper](https://arxiv.org/abs/2606.03264), [language list](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.en.md)

3. **dots.mocr** — единственный из shortlist, который прямо заявляет преобразование структурной графики в SVG-код; также выдаёт bounding boxes, типы блоков, текст, LaTeX для формул и HTML для таблиц. Это привлекательная исследовательская ветка для технической графики, но авторы сами отмечают ограничения по сложным формулам/таблицам и недостаточную надёжность SVG reconstruction. Модель около 3B параметров; на HF указана MIT, но репозиторий добавляет отдельное соглашение с ограничениями на некоторые варианты использования. Поддержка русского и Simplified/Traditional Chinese в проверенных источниках не определена как гарантированный перечень. [dots.mocr paper](https://arxiv.org/abs/2603.13032), [official repository and limitations](https://github.com/studio-dots-ai/dots.mocr), [license agreement](https://github.com/studio-dots-ai/dots.mocr/blob/main/dots.mocr%20LICENSE%20AGREEMENT)

Ни один рассмотренный вариант пока не подтверждает требование eOCR как целую систему: взять произвольный цифровой, сканированный или смешанный PDF, сохранить техническую графику и макет, создать структурно проверяемый редактируемый DOCX, выполнить всё только на локальном GPU и иметь доказуемый Lean scope до конкретных GPU kernels. Нужны фиксированные версии, прототип конвертера и измерения на собственном корпусе.

## 1. MinerU 4.1: наиболее полный parsing и rendering pipeline

По официальному release feed, на 4 ноября 2026 последний опубликованный релиз — MinerU 4.1.5 от 3 ноября. В релизе 4.1.4 добавлено распознавание inline formula crops VLM-путём в Standard/Advanced PDF text mode с per-crop MFR fallback. Это показывает, что маршрут сложной страницы составной, а не один forward pass модели. [MinerU releases](https://github.com/opendatalab/MinerU/releases)

**Реальный путь инференса.** Уровни качества разделяют native parsing и inference: Flash разбирает native PDF text/Office documents и использует Flash OCR для сканов; Basic подключает малые OCR/formula/table/layout модели; Standard сочетает малые модели с VLM для сложного layout; Advanced использует тот же состав моделей/runtime, но больше inference computation. PDF и изображения проходят любой из этих уровней. Форматы Office читаются как локальные документы на Flash. [Tiers and runtimes](https://opendatalab.github.io/MinerU/usage/tiers/)

Light model bundle раскрыт явно: PP-DocLayoutV2; PP-OCRv6 Tiny detector + Small recognizer; PP-OCRv4 mobile seal detector; PP-FormulaNet plus-M; SlanetPlus, UNet и PP-LCNet для таблиц. В ONNX FormulaNet autoregressive loop находится внутри графа. Model manifest хранит источники, ревизии, SHA-256, сигнатуры и данные проверки экспорта; официальный ONNX bundle описывает валидацию token sequences/LaTeX. [MinerU model assets](https://opendatalab.github.io/MinerU/zh/next/model-assets/), [ONNX asset card](https://huggingface.co/opendatalab/MinerU-4_models_onnx)

Результат — не только Markdown: общая document model содержит ordered pages/blocks и geometry, а рендеры включают DOCX, HTML, LaTeX, structured content и content lists. V1 Tasks/file-parse перечисляет DOCX как доступный output. PDF renderer может сохранить исходные страницы и позиции блоков при полной geometry либо перейти к semantic reflow; отдельной гарантии того же режима для DOCX renderer не заявлено. В Flash-путях display equations также используют image fallback в DOCX, поэтому формульное распознавание не означает редактируемое Word equation. DOCX export API существует, но точное воспроизведение PDF layout в Word не обещано. Изображения, таблицы и графики могут пройти как image assets. [Output contract](https://opendatalab.github.io/MinerU/reference/output_files/)

**Языки.** PP-OCRv6 Small покрывает Simplified Chinese, Traditional Chinese, English и латинские языки, но не русский. В текущих MinerU 4 model assets recognizer именно PP-OCRv6 Small. Документация MinerU не даёт отдельного измеренного списка языков для VLM OCR ветки, поэтому русское распознавание через Standard/Advanced — неизвестно, а не подтверждённое свойство кандидата. Ранние версии OCR не следует считать эквивалентом текущей 4.1 конфигурации. [MinerU asset list](https://opendatalab.github.io/MinerU/zh/next/model-assets/), [PP-OCRv6 languages](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.md)

**Локальный GPU и полнота runtime.** Есть выбор small backend и VLM engine; веса можно скачать, проверить и затем запускать с local model source/offline. Но GPU не означает выполнение каждого узла на GPU: MinerU docs говорят, что обычная OCR detection на Windows исполняется CPU, seal detection, table classification и SLANetPlus используют CPU; GPU MFR имеет CPU tail batches. ONNX device selection также может fallback на CPU. Следовательно eOCR придётся фиксировать конфигурацию и проверять фактические execution providers на каждой операции, иначе GPU-only runtime не обеспечен. [Tier runtime matrix](https://opendatalab.github.io/MinerU/usage/tiers/), [model source / offline path](https://opendatalab.github.io/MinerU/usage/model_source/), [device and asset details](https://opendatalab.github.io/MinerU/zh/next/model-assets/)

**Лицензия.** Код MinerU указывает Apache 2.0 с дополнительными условиями: отдельная коммерческая лицензия требуется при consolidated MAU свыше 100 млн или месячной выручке выше $20 млн; онлайн-сервис должен явно атрибутировать MinerU. HF model bundle указывает Apache-2.0 для Torch assets, тогда как ONNX card напоминает, что лицензии исходных моделей и атрибуция сохраняются. Нужно рассматривать лицензии проекта и каждого веса отдельно. Официальный MinerU2.5-Pro-2605 VLM card указывает Apache-2.0 и tags Chinese/English; это не подтверждает русский язык. [MinerU2.5-Pro-2605 model card](https://huggingface.co/opendatalab/MinerU2.5-Pro-2605-1.2B), [MinerU license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md), [Torch model bundle](https://huggingface.co/opendatalab/MinerU-4_models_torch), [ONNX model bundle](https://huggingface.co/opendatalab/MinerU-4_models_onnx)

**Ресурсы.** MinerU указывает минимум 16 GB системной памяти для higher-throughput local deployment; 8 GB VRAM названо только стартовой плановой величиной, без гарантии. Speed/memory зависит от VLM engine, размера входа и concurrency. Release даёт ориентир 2–3× CPU для representative core inference workloads, не end-to-end страницы с фиксированным GPU/разрешением и замером VRAM. [Resource/platform limits](https://opendatalab.github.io/MinerU/usage/tiers/), [4.1.0 release note](https://github.com/opendatalab/MinerU/releases)

## 2. PaddleOCR-VL-1.6: компактный parser с явно заявленным русским

**Модель и результат.** Авторская статья описывает двухступенчатую систему: PP-DocLayoutV3 выполняет layout analysis, затем PaddleOCR-VL-1.6-0.9B распознаёт локализованные text, tables, formulas, charts и seals. Лёгкая post-processing стадия строит Markdown/JSON, объединяет cross-page tables и уточняет heading hierarchy. В статье заявлен OmniDocBench v1.6 score 96.33%; это авторский benchmark, а не eOCR-specific accuracy. [PaddleOCR-VL-1.6 paper](https://arxiv.org/abs/2606.03264)

**Языки и формулы.** Алгоритмическая страница PaddleOCR-VL перечисляет 109 языков, включая Russian в Cyrillic перечне; текущая страница серии заявляет распознавание formulas/tables, а chart recognition по умолчанию выключен и включается параметром. Есть расхождение документации по версиям: release notes PaddleOCR 3.4/VL-1.5 говорят уже о 111 языках, включая Tibetan и Bengali; paper VL-1.6 не задаёт полный языковой перечень. Следовательно русский заявлен в официальном перечне серии, но фактический список конкретного checkpoint VL-1.6 следует подтвердить. В документах написано Chinese без уточнения Simplified/Traditional. [Language list and feature notes](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.en.md), [PaddleOCR 3.4 release notes](https://github.com/PaddlePaddle/PaddleOCR), [VL-1.6 paper](https://arxiv.org/abs/2606.03264)

**Путь исполнения.** Публичный pipeline принимает image или отдельный PDF path; official usage docs describe loading such as rendering PDF pages as images, followed by layout and VLM processing. Это указывает на raster-page inference; отдельного native embedded-text extraction path для born-digital PDFs в этой документации нет. Local direct inference документирован, доступны PaddlePaddle и Transformers engines и запуск на NVIDIA GPU. Первичный запуск автоматически скачивает веса; для отключённой сети есть offline Docker image, который нужно загрузить заранее. VLM server и API service также документированы, значит для локального режима потребуются locked image/model files и локальный endpoint. [PaddleOCR-VL usage](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md)

Для доказательства и воспроизводимости важно закрепить inference engine: официальная матрица указывает для NVIDIA PaddlePaddle/Transformers CC ≥ 7.0 и CUDA ≥ 11.8, а vLLM — CC ≥ 8.0 и CUDA ≥ 12.6; vLLM на CC 7.x может запускаться, но docs предупреждают о timeout/OOM. Без выбора backend модель не задаёт один GPU graph. [PaddleOCR-VL GPU requirements](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md)

**Вес и code license.** Model card PaddleOCR-VL-1.6 указывает Apache-2.0 и предоставляет local library usage. PaddleOCR/PaddlePaddle открывают pipeline и framework source. Это благоприятнее для аудита runtime, но для фактического полного proof scope дополнительно нужны закреплённые ревизии PaddleX, PaddlePaddle, model files, selected execution engine, CUDA/cuDNN and driver boundary. [HF model card](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6), [PaddleOCR source](https://github.com/PaddlePaddle/PaddleOCR), [PaddlePaddle GPU kernel example](https://github.com/PaddlePaddle/Paddle/blob/develop/paddle/phi/kernels/fusion/gpu/block_multi_head_attention_kernel.cu)

**DOCX и техническая графика.** Официальные PaddleOCR docs перечисляют DOCX export для PaddleOCR-VL series; usage API принимает outputFormats=docx. Это даёт готовый Word output путь, но docs описывают его как export parsed results for viewing/editing и не задают измеренные гарантии сохранения PDF page geometry, vector objects или формул как OMML. Chart understanding не равен восстановлению исходной графики; проверка DOCX по требованиям eOCR всё равно нужна. [PaddleOCR README](https://github.com/PaddlePaddle/PaddleOCR), [PaddleOCR-VL output formats](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md)

## 3. dots.mocr: отдельная ветка для структурной графики

**Функциональность.** Авторы представляют 3B-parameter multimodal OCR модель, предназначенную для совместного parsing текста и графики; paper сообщает 83.9 на olmOCR Bench и результаты image-to-SVG для charts, UI layouts, scientific figures, chemical diagrams. Эти цифры авторские и получены на их benchmark setup, не следует напрямую сравнивать с OmniDocBench 96.33 для PaddleOCR-VL-1.6. [dots.mocr paper](https://arxiv.org/abs/2603.13032)

Repository parser читает PDF или изображение, а выход включает JSON layout elements с bbox/category/text, Markdown и визуализацию layout. Prompt требует human reading order, LaTeX для formulas, HTML для tables. Из документации следует, что PDF parser является отдельным outer layer вокруг модели, поэтому доказуемый путь также содержит PDF page rendering/обработку. Авторы прямо указывают, что сложные tables/formulas остаются трудными и SVG reconstruction ещё недостаточно надёжна. [Parser, outputs and limitations](https://github.com/studio-dots-ai/dots.mocr)

**Graphics relevance.** Image-to-SVG режим — единственное явно заявленное восстановление graphic в кодоподобную структуру среди shortlist. Но output SVG является генерируемой моделью реконструкцией области, а не оригинальным vector object из PDF. Это может лучше сохранить семантику схемы, но фактическая точность, редактируемость в DOCX и соответствие исходным линиям/подписям неизвестны. [Repository graphics notes](https://github.com/studio-dots-ai/dots.mocr), [paper](https://arxiv.org/abs/2603.13032)

**Локальный GPU, веса и лицензия.** Repository публикует vLLM и Transformers paths, локальный CUDA-пример, загрузку весов, режимы document parsing и image-to-SVG. HF card помечает веса MIT и предоставляет Transformers/vLLM usage. При этом репозиторий распространяет дополнительное dots.mocr License Agreement поверх MIT; среди прочего оно ограничивает неавторизованную digitization/copyrighted publication scanning/bulk scraping и задаёт условия для чувствительных данных. Применимость к eOCR зависит от назначения и прав на документы, поэтому лицензионная оценка обязательна. [vLLM setup and README](https://github.com/studio-dots-ai/dots.mocr), [HF model card](https://huggingface.co/dots-studio/dots.mocr), [license agreement](https://github.com/studio-dots-ai/dots.mocr/blob/main/dots.mocr%20LICENSE%20AGREEMENT)

HF tags перечисляют multilingual, English и Chinese, но официальная карточка не даёт закрытого списка языков для русского, simplified/traditional китайского. Картинки с языковыми примерами или общая multilingual маркировка не подтверждают требуемую точность. [dots.mocr model card](https://huggingface.co/dots-studio/dots.mocr)

## 4. Подпись — отдельный визуальный объект, не OCR text

По уточнённой области v1 рукописный текст исключён, но изображение подписи необходимо обнаружить, вырезать из исходной страницы и вставить в DOCX как raster image. Подпись может иметь bounding box, confidence и исходные координаты, но её чернила нельзя передавать в этап распознавания текста как ожидаемый текстовый блок. Не следует считать подпись печатью: MinerU и PaddleOCR явно имеют классы seal/stamp, а это другой объект.

В документации и категориях трёх кандидатов нет явного signature-класса:

| Кандидат | Документированные категории | Вывод для подписи |
|---|---|---|
| MinerU 4.1 / PP-DocLayoutV2 | PP-DocLayoutV2 перечисляет image, seal и layout labels, но не signature; в MinerU также отдельная обработка seal. | Dedicated signature detection не подтверждён. Нужен отдельный detector или fine-tuning; общий image box не гарантирует отдельную подпись. |
| PaddleOCR-VL-1.6 / PP-DocLayoutV3 | PaddleOCR layout categories включают image, chart и seal; VLM docs заявляют seal recognition, но не signature class. | Нужен отдельный подпись-детектор или fine-tuning; не путать распознавание печати с подписью. |
| dots.mocr | Layout prompt categories включают Picture, но не signature. | Общий picture detection или graphic-to-SVG не подтверждают reliable signature localisation; нужен отдельный detector/fine-tuning. |

Источники: [MinerU PP-DocLayoutV2 labels](https://github.com/opendatalab/MinerU/blob/master/mineru/model/layout/pp_doclayout_v2_base.py), [MinerU seal handling](https://github.com/opendatalab/MinerU/blob/master/mineru/backend/pipeline/batch_analyze.py), [PaddleOCR layout categories](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/module_usage/layout_detection.en.md), [PaddleOCR-VL features](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.en.md), [dots.mocr layout prompt and outputs](https://github.com/studio-dots-ai/dots.mocr).

Для каждого кандидата следует рассматривать отдельный object detector, обученный или дообученный на аннотациях signature regions, и измерять recall/false positives отдельно от handwritten annotations, печатей, инициалов, checkbox marks и пометок. Его результат — source-page crop и координаты; crop сохраняется в raster виде в DOCX и исключается из OCR текста. Остаётся выяснить, существует ли подходящий публичный signature detector с нужной лицензией и доказуемым runtime.
## 5. Lean proof scope и GPU kernels

Граница доказательства должна описывать полный inference runtime, соответствующий термину проекта «инференсный runtime»: обработка файла/PDF и rasterization; нормализация, cropping и layout preprocessing; точные модели и weights; inference graph; decoding; ordering и parsing результата; материализация assets; DOCX rendering. Для GPU пути к этому добавляются выбранные framework/engine, CUDA kernels, сборка kernels, compiler flags, device libraries, runtime, driver и модель аппаратного исполнения.

У всех трёх кандидатов есть публичный код и открытые компоненты model graph/kernels, но не найдено формальной спецификации и Lean proof для всей этой цепочки. Наличие исходников позволяет определить объект анализа; оно не является доказательством, что установленный binary соответствует этим исходникам или что конкретные kernel execution traces корректны.

- **MinerU ONNX path** даёт относительно ясные model graphs, asset revisions/hashes, signatures и export validation. Однако provider dispatch может быть DirectML/WebGPU/CUDA/CPU, есть CPU этапы, а приложение зависит от ONNX Runtime и всей host-side обработки. ONNX Runtime публикует CUDA execution provider source, но доказательства provider/kernel/compiler/driver связности нет. [MinerU ONNX assets](https://huggingface.co/opendatalab/MinerU-4_models_onnx), [ONNX Runtime CUDA provider](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/cuda_execution_provider.cc)

- **PaddleOCR-VL** предоставляет pipeline и framework source; CUDA GPU kernel implementations доступны, например в PaddlePaddle. При переходе на vLLM/другие engines состав операторов меняется. Документация vLLM говорит, что distribution содержит precompiled C++/CUDA binaries и для производительности собирает много CUDA kernels; binary compatibility зависит от CUDA и PyTorch build. Поэтому доказательство потребует избрать один execution engine и зафиксировать toolchain. [Paddle CUDA kernel source](https://github.com/PaddlePaddle/Paddle/blob/develop/paddle/phi/kernels/fusion/gpu/block_multi_head_attention_kernel.cu), [vLLM CUDA installation notes](https://github.com/vllm-project/vllm/blob/main/docs/getting_started/installation/gpu.cuda.inc.md)

- **dots.mocr** имеет открытые model/inference source и использует Qwen/Transformers или vLLM. В vLLM CUDA kernels и compiled engine входят в доверенную базу до отдельного анализа; trust_remote_code в опубликованном Transformers примере добавляет исполняемый model repository code. [dots.mocr inference source](https://github.com/studio-dots-ai/dots.mocr), [vLLM CUDA installation notes](https://github.com/vllm-project/vllm/blob/main/docs/getting_started/installation/gpu.cuda.inc.md)

Практичный proof boundary для следующего этапа: выбрать один точный checkpoint, format, parser, backend, precision, batch/concurrency и GPU; сохранить hash weights/source/build; экспортировать или извлечь операторный граф; перечислить каждый operator и его CPU/GPU implementation; замкнуть kernel/build/runtime assumptions как доверенную базу или доказать соответствующие refinement properties. Lean может доказать корректность структурной проверки относительно заданной эталонной аннотации; такая теорема не устанавливает истинность самой аннотации или распознанного текста.

## 6. Скорость, память и воспроизводимость

| Кандидат | Публичные ресурсные сигналы | Что остаётся неизвестным |
|---|---|---|
| MinerU 4.1 | 16 GB system RAM как рекомендация для higher-throughput local deployments; 8 GB VRAM только как стартовая оценка. Примерная скорость core inference 2–3× CPU в 4.1 release. | Нет фиксированной карты GPU, DPI, разрешения, страниц/с, p50/p95, VRAM peak или полного времени PDF→DOCX; версия/engine/concurrency влияют. |
| PaddleOCR-VL-1.6 | 0.9B параметров; опубликованы benchmark accuracy scores и hardware matrix по compute capability/CUDA. | Не найдено воспроизводимого per-page latency или peak VRAM для VL-1.6 на фиксированном GPU. Размер offline Docker image — размер дискового образа, а не требование VRAM. |
| dots.mocr | 3B параметров; README задаёт vLLM gpu-memory-utilization=0.9 и локальный CUDA/vLLM путь. | 0.9 — доля бюджета vLLM, а не замер в гигабайтах; нет опубликованного полного PDF page latency/peak VRAM с фиксированным протоколом. |

Benchmark score не заменяет измерения eOCR: Paddle paper оценивает OmniDocBench v1.6, MinerU даёт качественный ресурсный ориентир, а dots.mocr сообщает собственные comparative sets. Сравнение требует общей версии/кропа/разрешения и одинакового hardware/runtime.

## 7. Неизвестные и вопросы для следующей оценки

1. Какой конкретный GPU, минимальный VRAM, поддерживаемая OS и допустимые версии драйвера/CUDA? Должен ли CPU быть запрещён для всех preprocessing и postprocessing узлов, или только для нейросетевого inference?
2. Какова фактическая точность русских технических документов и смешанного текста Ru/En/CN? Отдельно проверить Simplified и Traditional Chinese; общая метка «Chinese» недостаточна.
3. Для формул: нужен editable Word equation (OMML), LaTeX/MathML с конвертацией, либо исходный crop fallback? Поддерживают ли кандидаты нужные inline/display equations?
4. Для технической графики: сохранять исходный PDF crop как image, переносить vectors из PDF, или генерировать SVG реконструкцию? У каждого пути разные гарантии и время.
5. DOCX layout contract: какие допуски по координатам, размерам шрифта, колонкам, page breaks и порядку блоков допустимы? MinerU DOCX renderer этого требования автоматически не подтверждает.
6. Необходимо отдельное измерение по открытым sample PDFs: page/s; wall-clock p50/p95; VRAM peak; CPU RAM; energy/thermal (если существенно); страницы разных DPI/сложности; задержка cold start и warm runtime. Записывать также model hashes, inference engine, precision, concurrency, output format и CPU fallback.
7. Какой отдельный signature detector нужен, не смешивая подписи с печатями и рукописными аннотациями; какие crop/placement допуски и recall/false-positive метрики нужны?
8. Перед Lean proof надо решить, входят ли PDF parser, rasterizer, Python host code, tokenizer/model runtime, GPU kernel compiler/driver и GPU ISA semantics в доказуемый код или объявленный trust boundary.

**Shortlist для решения пользователя:** MinerU 4.1 — если важен готовый end-to-end document stack и DOCX output; PaddleOCR-VL-1.6 — если приоритетны русский и документный VLM parsing; dots.mocr — если нужно отдельно исследовать модельную реконструкцию технических graphics в SVG. Это не рекомендация выбрать один из них: неизвестные выше меняют порядок кандидатов.
