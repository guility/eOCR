# Signature-region detection for raster crops

**Date:** 2026-11-04
**Scope:** eOCR must locate a visible handwritten signature in a source PDF and carry it into DOCX as a raster crop at the source page position. This is region localization and appearance preservation; it is separate from handwriting transcription, signer identification, signature verification, and cryptographic PDF signatures.

## Finding

PaddleOCR’s PP-DocLayout is not a pretrained signature detector. The published PP-DocLayout-L/M/S label set has 23 classes, including `seal` but not `signature`; the newer PP-DocLayoutV3 list has 25 classes and likewise no signature class. PaddleOCR describes seal text detection/recognition as a separate seal pipeline, so the seal class is not a proxy for handwritten signatures. ([PP-DocLayout model and labels](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/seal_recognition.en.md), [PP-DocLayoutV3 labels](https://paddlepaddle.github.io/PaddleX/latest/en/module_usage/tutorials/ocr_modules/layout_analysis.html))

For this requirement, use a one-class object detector to produce signature boxes. The detector does not produce a clean transparent signature cutout: eOCR still needs to crop the rendered page pixels inside the box and map that box from render pixels back to PDF page coordinates before placing the crop in DOCX.

## Data, provenance, and access

The Tech4Humans card describes 2,819 images: 1,980 train, 420 validation, and 419 test, resized to 640×640, with augmentations. It declares Apache-2.0, but the source mix is Tobacco800 plus `signatures-xc8up`. The underlying Roboflow 100 source has 368 images and is labeled CC BY 4.0. Tobacco800 is a subset of the CDIP document collection; NIST describes CDIP as scanned documents from the tobacco-industry litigation archive and its catalog points to a NIST open-license page. The sources reviewed do not explain how that NIST grant applies to those underlying archive pages. Treat the composite card’s Apache-2.0 label as the uploader’s declaration and verify source-image terms before redistributing the data or derived weights. ([Tech4Humans dataset card](https://huggingface.co/datasets/tech4humans/signature-detection), [Roboflow 100 source](https://universe.roboflow.com/roboflow-100/signatures-xc8up), [Tobacco800 catalog](https://tc11.cvc.uab.es/datasets/Tobacco800_1), [NIST CDIP record and license field](https://catalog.data.gov/dataset/complex-document-information-processing-cdip-dataset), [NIST licensing statements](https://www.nist.gov/open/license))

The Tech4Humans dataset files are gated: Hugging Face requires the user to agree to share profile information before file access, although the card and file listing are public. The YOLOS cards’ sample code loads `samuellimabraz/signature-detection`, while their metadata and training description name `tech4humans/signature-detection`; verify whether that alias is the same dataset and what terms apply rather than assuming it removes the gate. ([Gated file listing](https://huggingface.co/datasets/tech4humans/signature-detection/tree/main/full), [YOLOS-small card](https://huggingface.co/mdefrance/yolos-small-signature-detection))

Other public data is smaller or carries different terms. Ultralytics documents a 178-image signature set (143 train, 35 validation, one class) under AGPL-3.0; it is a starter rather than a broad, independent validation corpus. ([Ultralytics signature dataset](https://github.com/ultralytics/ultralytics/blob/main/docs/en/datasets/detect/signature.md))

## Benchmark limits and open issues

- The candidate cards report results on one small dataset and do not show independent validation on eOCR’s PDFs. The Tech4Humans card gives an image split but does not document source-document grouping or whether augmentation happened before splitting, so the sources reviewed do not establish cross-document independence or rule out leakage.
- Model-card metrics and timing use different reporting paths and hardware. For example, YOLOS timings are on an i7-9750H/GTX 1650; the Conditional DETR project lists an ONNX CPU result without its CPU model; the YOLOv8 tuned latency is ONNX CPU and TensorRT/T4. Do not rank these latencies as equivalent measurements. ([YOLOS results](https://huggingface.co/mdefrance/yolos-small-signature-detection), [Conditional DETR experiments](https://huggingface.co/tech4humans/conditional-detr-50-signature-detector), [YOLOv8 results](https://huggingface.co/tech4humans/yolov8s-signature-detector))
- As checked on 2026-11-04, the YOLOS training repository lists zero open GitHub issues. The gated Tech4Humans YOLOv8 model has open Hugging Face discussions about access to weights and inference code. A separate Tech4AI Triton-server repository has an open licensing question about an Apache-2.0 claim alongside use of Ultralytics/AGPL; the author comment does not resolve that issue. This is a caution for the YOLOv8/server path, separate from the Conditional DETR and YOLOS Apache-2.0 declarations. ([YOLOS issues](https://github.com/mdefrance/signature-detection/issues), [YOLOv8 model discussions](https://huggingface.co/tech4humans/yolov8s-signature-detector/discussions), [open server licensing issue #11](https://github.com/tech4ai/t4ai-signature-detect-server/issues/11))

## Local smoke run

After collecting the public benchmark evidence above, the pinned YOLOS-tiny checkpoint was run once on the synthetic eOCR fixture using an NVIDIA RTX 5090. The checkpoint revision was `b788cf7376464453c3dea1e5ee8589adcaa0c634`; the container used PyTorch 2.13.0+cu130, Transformers 5.19.0, and Pillow 13.0.0. Ten forward passes after three warmups measured 4.405 ms p50 / 4.872 ms mean and 83.65 MiB peak CUDA allocated memory. This is model-forward-only timing on one small synthetic page, not a pipeline benchmark or a representative quality estimate.

At a 0.25 score threshold, the model emitted two overlapping detections. The highest score was 0.6484 with IoU 0.5681 against the fixture's PAGE reference box; its unpadded box missed part of the signature's right tail. A 10% width/height padding produced crop bounds `[88.63, 473.24, 462.55, 550.52]`, which contain the full synthetic reference region. That padded crop was substituted into a copy of the PAGE XML and passed through the existing DOCX builder. The resulting raster signature crop is an integration smoke check only; the text, math, and diagram still use oracle annotations.

Reproduce the detector and DOCX integration using the scripts/artifacts under `prototype/`; model weights are cached locally and are not checked in. Do not infer recall, false-positive rate, or generalization from this single generated example.

## Recommended next candidate and experiment

Compare `mdefrance/yolos-small-signature-detection` against the now smoke-tested YOLOS-tiny on a representative, labeled eOCR holdout. The small model remains a plausible accuracy/size candidate; tiny is now a verified integration baseline, not a selected production model. Add Conditional DETR if both YOLOS variants miss the required recall. Defer the YOLOv8s checkpoint until its weight gate and licensing path are acceptable.

Use a representative, labeled eOCR holdout of source PDF pages rendered at a fixed DPI. Measure per-signature recall, false positives per page, box IoU, and crop quality; include blank/unsigned pages, stamps, handwriting, printed names, and signatures in mixed/vector content. Separately verify page-coordinate mapping and raster crop placement. Before any later redistribution, resolve the dataset’s source-image licensing and reproduce the model’s claimed test metrics.
